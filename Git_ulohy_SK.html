Git - praktické úlohy

Zadania sú rozdelené na dva dni. Každá úloha je približne na 20 minút samostatného skúšania. Riešenie je skryté pod úlohou a dá sa odkryť až po práci.

Deň 1 Deň 2

Deň 1 - slidy 1 až 44

Version control, inštalácia, repository, commit, staging area, diff, .gitignore, HEAD, reset a revert.

1. Ručné verzie súboru

cca 20 minversion control

Vytvorte si priečinok bez-gitu a v ňom textový súbor navrh.txt. Napíšte doň krátky opis malej aplikácie alebo webu. Potom vytvorte tri kópie súboru s rôznymi názvami, napríklad navrh-final.txt, navrh-final2.txt a navrh-oprava.txt. Do každej verzie urobte malú zmenu.

Vašou úlohou je zistiť, ktorá verzia je najnovšia, čo sa v nej zmenilo a prečo by bol tento spôsob pri reálnom projekte problém.

Riešenie

Podľa názvov súborov sa história spravuje zle. Chýba presný čas zmeny, autor, dôvod zmeny a spoľahlivý diff medzi verziami. Git tento problém rieši cez commity, ktoré ukladajú konkrétny stav projektu spolu s metadata.

2. Overenie Gitu a základná konfigurácia

cca 20 mingit config

Otvorte terminál alebo Git Bash. Overte, či máte nainštalovaný Git, a nastavte meno a e-mail, ktoré sa budú zapisovať do commitov.

Riešenie 
git --version
git config --global user.name "Meno Priezvisko"
git config --global user.email "meno@example.com"
git config --global --list

Vo výstupe má byť vidieť user.name a user.email. Tieto údaje sa ukladajú do commit metadata.

3. Vytvorenie prvého repository

cca 20 mingit init

Vytvorte nové repository s názvom git-den1. V ňom vytvorte súbor README.md, napíšte doň nadpis a krátky opis projektu. Potom spravte prvý commit.

Riešenie 
git init git-den1
cd git-den1
git status

Vytvorte alebo upravte README.md, potom:

git add README.md
git commit -m "Add README"
git log --oneline
git status

git log --oneline má ukázať jeden commit a git status má hlásiť čistý working tree.

4. Staging area: commit iba vybraného súboru

cca 20 minstaging area

V repository vytvorte dva súbory: plan.txt a poznamky.txt. Do oboch napíšte nejaký text. Prvý commit má obsahovať iba plan.txt. Druhý commit má obsahovať poznamky.txt.

Riešenie 
git status
git add plan.txt
git status
git commit -m "Add plan"
git add poznamky.txt
git commit -m "Add notes"
git log --oneline

Commit berie obsah zo staging area. To, čo nie je staged, do commitu nejde.

5. Upravený súbor bez git add

cca 20 mincommit

Upravte README.md. Skúste hneď spraviť commit bez git add. Prečítajte si výstup Gitu a potom postup opravte.

Riešenie 
git status
git commit -m "Update README"

Git pravdepodobne oznámi, že nie je čo commitnúť, pretože zmena je iba vo working directory.

git add README.md
git commit -m "Update README"
git status

Po git add je zmena v staging area a commit prejde.

6. Porovnanie git diff a git diff --staged

cca 20 mindiff

Upravte existujúci súbor. Najprv si zmenu pozrite cez git diff. Potom ju dajte do staging area a porovnajte výstup git diff a git diff --staged.

Riešenie 
git diff
git add README.md
git diff
git diff --staged
git commit -m "Update README text"

git diff bez argumentov ukazuje rozdiel medzi working directory a staging area. Po git add môže byť prázdny. git diff --staged ukazuje staged zmeny oproti poslednému commitu.

7. Ignorovanie súborov cez .gitignore

cca 20 min.gitignore

Vytvorte súbor debug.log a priečinok build. Nastavte repository tak, aby Git tieto súbory neponúkal na commit.

Riešenie

Do súboru .gitignore vložte:

build/
*.log

Potom:

git status
git add .gitignore
git commit -m "Add gitignore"
git status

debug.log a build/ by sa už nemali zobrazovať ako untracked files.

8. Zahodenie necommitnutej zmeny

cca 20 minrestore

Upravte README.md tak, že doň pridáte zámerne zlý text. Pozrite si diff a potom zmenu zahoďte tak, aby sa súbor vrátil do stavu posledného commitu.

Riešenie 
git diff
git restore README.md
git status

Starší zápis je:

git checkout -- README.md

Pred zahodením zmeny je dobré vždy spustiť git diff, lebo necommitnutá zmena sa po zahodení nemusí dať jednoducho obnoviť.

9. Vybratie súboru zo staging area

cca 20 minreset

Upravte dva súbory a pridajte oba cez git add .. Potom jeden súbor vyberte zo staging area tak, aby jeho obsah v súbore ostal nezmenený. Commit má obsahovať iba druhý súbor.

Riešenie 
git add .
git status
git restore --staged README.md
git status
git commit -m "Commit only selected file"

Starší zápis je:

git reset -- README.md

Týmto sa súbor vyberie zo staging area, ale zmena vo working directory ostane.

10. Vrátenie commitu cez revert

cca 20 minrevert

Vytvorte súbor omyl.txt, commitnite ho a potom tento commit vráťte cez git revert. História sa nemá prepísať, má pribudnúť nový commit.

Riešenie 
git add omyl.txt
git commit -m "Add file by mistake"
git log --oneline
git revert <hash-commitu>
git log --oneline

V histórii má ostať pôvodný commit aj nový revert commit. To je vhodné najmä pri zmene, ktorá už mohla byť pushnutá alebo zdieľaná.

Deň 2 - slidy 45 až 88

Branches, merge, conflicts, remote repository, clone, push, fetch, pull, stash, tag a rebase.

1. Vytvorenie branchu

cca 20 minbranch

V repository z prvého dňa vytvorte branch feature/profil. Na tomto branchi vytvorte súbor profil.txt, commitnite ho a potom sa prepnite späť na hlavný branch.

Riešenie 
git branch
git checkout -b feature/profil

Vytvorte profil.txt, potom:

git add profil.txt
git commit -m "Add profile"
git checkout main
git log --oneline --graph --all

Ak sa hlavný branch volá master, použite git checkout master.

2. Merge bez conflictu

cca 20 minmerge

Spravte merge branchu feature/profil do hlavného branchu. Potom si pozrite históriu v grafickom výpise.

Riešenie 
git checkout main
git merge feature/profil
git log --oneline --graph --all

Ak hlavný branch nemal nové commity, Git môže spraviť fast-forward merge. Výsledok je, že zmeny z feature branchu sú už aj na hlavnom branchi.

3. Vytvorenie merge conflictu

cca 20 minconflict

Vytvorte situáciu, v ktorej sa rovnaký riadok rovnakého súboru zmení inak v dvoch branchoch. Potom skúste merge.

Riešenie 
git checkout main
echo "farba: modra" > menu.txt
git add menu.txt
git commit -m "Add menu"

git checkout -b feature/menu
echo "farba: zelena" > menu.txt
git add menu.txt
git commit -m "Change menu color in feature"

git checkout main
echo "farba: cervena" > menu.txt
git add menu.txt
git commit -m "Change menu color in main"

git merge feature/menu

Git má zahlásiť conflict v súbore menu.txt.

4. Vyriešenie merge conflictu

cca 20 minconflict markers

Otvorte súbor s conflictom, vyberte finálnu verziu riadku, odstráňte conflict markers a dokončite merge.

Riešenie

V súbore menu.txt odstráňte riadky s <<<<<<<, ======= a >>>>>>>. Nechajte iba výsledný obsah, napríklad:

farba: cervena a zelena

Potom:

git status
git add menu.txt
git commit
git status
git log --oneline --graph --all

git add tu znamená, že súbor je vyriešený a pripravený na dokončenie merge.

5. Mazanie branchov

cca 20 mingit branch -d

Zobrazte si lokálne branches. Vymažte branch, ktorý už bol merged. Potom vytvorte nový branch s jedným commitom a skúste ho zmazať bezpečným spôsobom cez -d.

Riešenie 
git branch
git branch -d feature/profil

git checkout -b experiment
echo "pokus" > experiment.txt
git add experiment.txt
git commit -m "Add experiment"
git checkout main
git branch -d experiment

Git by mal odmietnuť zmazať branch experiment, ak ešte nebol merged. Nútený variant je git branch -D experiment, ale ten použite iba vtedy, keď naozaj chcete zahodiť daný branch.

6. Clone remote repository

cca 20 minclone

V GitLabe alebo inom Git serveri vytvorte prázdne remote repository. Spravte clone, skontrolujte remote alias a pushnite prvý commit.

Riešenie 
git clone <url>
cd <nazov-repository>
git remote -v

Vytvorte README.md, potom:

git add README.md
git commit -m "Add README"
git push

Ak Git pýta upstream branch:

git push -u origin main

Ak sa branch volá master, použite master.

7. Rozdiel medzi fetch a pull

cca 20 minfetch / pull

Urobte zmenu v remote repository cez webové rozhranie alebo z druhého clone. V pôvodnom clone najprv použite git fetch, pozrite históriu a až potom použite git pull.

Riešenie 
git fetch
git log --oneline --graph --all
git status
git pull
git log --oneline --graph --all

fetch stiahne nové informácie z remote repository, ale nemení aktuálny working directory. pull spraví fetch a potom zmeny zapracuje do aktuálneho branchu.

8. Odmietnutý push a následný pull

cca 20 minpush / pull

Simulujte situáciu, že remote repository už obsahuje commit, ktorý lokálne ešte nemáte. Potom skúste pushnúť vlastný commit a vyriešte situáciu cez pull.

Riešenie

Postup môže byť takýto:

  1. V remote repository upravte súbor cez web a commitnite zmenu.
  2. Lokálne upravte iný riadok alebo iný súbor.
  3. Lokálne spravte commit.
  4. Skúste git push.
git add .
git commit -m "Local change"
git push
git pull
git push

Prvý push môže zlyhať, pretože remote branch je ďalej. Po git pull sa remote zmeny zapracujú lokálne a ďalší push môže prejsť.

9. Dočasné odloženie práce cez stash

cca 20 minstash

Upravte súbor, ale necommitujte ho. Odložte rozpracovanú zmenu cez git stash, prepnite branch a potom sa vráťte späť k odloženej zmene.

Riešenie 
git status
git stash
git status
git stash list
git checkout main
git checkout <povodny-branch>
git stash pop
git status

stash je dočasné odloženie rozpracovaných zmien. Nie je to náhrada za normálny commit.

10. Tag a jednoduchý rebase

cca 20-30 mintag / rebase

Označte aktuálny commit tagom v1.0.0. Potom vytvorte branch s dvoma commitmi, na hlavnom branchi spravte ďalší commit a skúste feature branch presunúť cez rebase.

Riešenie 
git tag v1.0.0
git tag

git checkout -b feature/rebase-demo

Spravte dva malé commity na feature/rebase-demo. Potom:

git checkout main

Spravte jeden commit na main. Potom:

git checkout feature/rebase-demo
git rebase main
git log --oneline --graph --all --decorate

Rebase prepíše lokálnu históriu feature branchu tak, že jeho commity položí na nový základ. Nerobte rebase zdieľanej histórie, ktorú už používajú iní ľudia.

Súbor je určený na zdieľanie s účastníkmi. Riešenia sú predvolene skryté a dajú sa otvoriť jednotlivo alebo tlačidlami hore.
